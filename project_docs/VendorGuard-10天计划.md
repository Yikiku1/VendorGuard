# VendorGuard 10 天计划

> 内容类型：一期 MVP 精简执行计划
>
> 时间预算：10 天
>
> 配套文档：[PRD](./VendorGuard-PRD.md)、[前期调研与需求分析](./VendorGuard-前期调研与需求分析.md)

## 冲刺原则

本计划固定 10 天日历期限，同时将一期收缩为一条完整准入主线和一条最小采购例外支线。核心保留确定性规则、提交人与审批人隔离、追加式审计、三类固定模板解析、基础混合检索、两个受控 Agent、最小节点恢复、三个简化案例和自动化测试。

压缩方式不是跳过测试或夸大能力，而是限制模板、角色、规则、页面和异常覆盖。实现范围必须区分“已定义”“已实现”“已验证”，未进入本期的质量经理、管理员、双人审批和复杂后台不得写成已交付功能。

每天建议按以下节奏执行，休息时间不计入工时：

| 时间 | 内容 |
| --- | --- |
| 30 分钟 | 确认当天目标、接口和验收项 |
| 2.5 小时 | 第一段核心实现 |
| 2 小时 | 第二段实现或模块串联 |
| 1.5 小时 | 自动化测试、错误路径和修复 |
| 30 分钟 | 文档、代码检查、提交和次日准备 |
| 0 至 1 小时 | 当天缓冲，只处理阻塞与验收失败 |

每天结束时必须留下可运行、可测试的状态。若当天未通过完成判定，第二天先修复，不允许同时开启三个以上未完成模块。

## 每日完成定义

一天只有同时满足下列条件才标记完成：

- 实现位于正确业务模块，规则没有写入路由、Prompt 或前端。
- 新行为有自动化测试，相关测试在本机通过。
- Ruff、mypy 对变更范围无新增错误。
- 数据库变化有 Alembic 迁移，迁移可从空库执行。
- 没有提交 `.env`、密码、Token、真实供应商数据、日志或本地数据库。
- 接口、配置或运行方式变化时，同步更新对应文档。
- 当天交付物能由另一人按照说明复现。

## M1：工程与数据基础

### Day 1：冻结领域基线并建立可运行工程

**目标工时：9 至 10 小时**

**任务**

- 整理五类状态的数据字典：供应商资格、准入案件、采购例外案件、工作流运行和证据充分性。
- 为三个演示案例定义输入材料、结构化事实、预期规则命中、审批人、最终状态和审计事件。
- 固化 `VEN-001` 至 `VEN-006`、`PR-001` 的字段、运算符、阈值和边界样例。
- 配置 `src` 包、`uv` 依赖组、Ruff、mypy、pytest 和 `.env.example`。
- 实现 `pydantic-settings` 配置、FastAPI 应用工厂、`/health` 和统一错误响应。
- 基于 `ContextVar` 实现包含 `request_id` 的 JSON 日志，不复制 `flo_prj` 的根日志器和线程本地实现。

**交付物**

- 数据字典、三个结构化案例和第一版规则测试表。
- 可启动后端、配置模块、日志模块、基础测试和 `uv.lock`。

**完成判定**

- 每条规则至少有一个命中、一个不命中和一个边界案例。
- 新终端可启动服务并访问 `/health`。
- 并发请求的 `request_id` 不串线，异常响应不泄露内部异常原文。
- 基础 pytest、Ruff 和 mypy 通过。

### Day 2：PostgreSQL、迁移、认证与权限

**目标工时：跨 Day 2 与 Day 3 上午收尾，不追加当晚工作**

**任务**

- 编写 PostgreSQL + pgvector 的初版 `compose.yaml`，固定镜像标签和健康检查。
- 建立 SQLAlchemy Async Engine、请求级 Session、连接池和事务管理。
- 初始化 Alembic，创建用户表和角色约束的第一版迁移。
- 实现预置用户、Argon2 密码哈希、JWT 签发和解析。
- 保留四个领域角色定义，只为采购专员和采购经理创建演示账号并实现认证依赖。
- “提交人不能审批自己的案件”随 Day 4 审批用例实现，不在 Day 2 提前铺开。

**交付物**

- PostgreSQL 容器、数据库适配器、Alembic 配置和首个迁移。
- 登录接口、两个预置用户和基础认证测试。

**完成判定**

- 空数据库可以升级到最新迁移，回退一次后可再次升级。
- 正确凭据返回 Token；错误凭据、过期 Token 和伪造 Token 均被拒绝。
- JWT 密钥来自环境配置，仓库中不存在硬编码密钥和 MD5。
- 应用关闭后不遗留数据库连接，集成测试可重复运行。

**2026-08-30 当前进度**

- PostgreSQL + pgvector 容器、请求级 Session、应用生命周期、Alembic 和显式角色约束已经完成验证。
- Argon2、JWT 签发/解析与安全边界、两个演示账号的真实幂等种子和认证核心已经完成。
- 本地种子首次创建 2 个账号，再次执行创建 0 个账号；仓库不包含真实密码或 JWT 密钥。
- `/auth/login`、Bearer Token 认证依赖和 `/auth/me` 已完成。
- 2026-08-31 联合验收：pytest 51 passed，Ruff、mypy、`git diff --check` 和 `alembic check` 全部通过，Day 2 完成。

## M2：两条业务闭环

### Day 3：建立最小案件模型

**目标工时：约 6 至 7 小时**

**任务**

- 实现 `Supplier`、`AdmissionCase`、`Document` 和 `AuditEvent` 最小模型与迁移。
- 实现创建供应商、创建准入案件和查询案件详情接口。
- 保存附件元数据、SHA-256、类型和大小；暂不实现通用文件存储平台。
- 对创建案件、上传材料和状态变化追加审计事件。

**交付物**

- 登录接口、`suppliers.py`、`admission` 和 `audit.py` 的首批接口与集成测试。

**完成判定**

- 两个演示账号可以登录，采购专员可以创建准入案件。
- 可以查询材料清单与追加式审计时间线。
- 非法状态迁移和重复材料被拒绝。

**2026-09-01 当前进度（已完成）**

- `Supplier`、`AdmissionCase`、`Document`、`AuditEvent` 最小模型及四个连续 Alembic 迁移已实现。
- 同案件材料 SHA-256 重复约束、审计事件追加与顺序查询已经验证。
- PostgreSQL 触发器已验证禁止更新和删除审计事件。
- `POST /api/admission/suppliers` 已实现并验证，只有采购专员可以创建候选供应商，重复信用代码返回 409。
- `POST /api/admission/cases` 已实现并验证，只有采购专员可以基于已有供应商创建 `draft` 案件；采购经理返回 403，不存在的供应商返回统一 404。
- 案件绑定当前提交人，并在同一事务追加 `admission_case_created` 审计事件；接口测试使用事务回滚，不污染本地案件和审计数据。
- `POST /api/admission/cases/{case_id}/documents` 已实现并验证，仅采购专员可以登记材料元数据；采购经理返回 403，不存在的案件返回统一 404，同案件重复 SHA-256 返回 409。
- 材料登记与 `documents_registered` 审计事件在同一事务完成，接口测试覆盖成功、权限、案件存在性、数据库唯一约束和事务回滚。
- `GET /api/admission/cases/{case_id}` 已实现并验证，采购专员可以查询案件、供应商、材料元数据列表和追加式审计时间线；不存在的案件返回统一 404。
- `POST /api/admission/cases/{case_id}/transition` 已实现并验证，当前支持 `draft -> pending_documents`；合法迁移追加 `admission_case_status_changed` 审计事件。
- 非法迁移返回 409 且状态保持不变、成功状态审计不追加；采购经理迁移返回 403。
- 联合验收为 pytest 71 passed，Ruff lint/format、mypy、`git diff --check` 和 `alembic check` 全部通过。
- 实际文件存储仍未实现，材料接口当前只保存元数据；Day 4 规则与审批尚未开始。

## M3：解析、证据与编排

### Day 5：PDF、XLSX、CSV 解析与确定性计算

**目标工时：约 6 至 7 小时**

**任务**

- 实现一套固定营业执照 PDF 模板的页级解析、文件哈希、解析状态和来源定位。
- 实现一套固定 XLSX 报价模板和一套固定 CSV 履约模板，保存单元格或行号。
- 实现币种、单位、含税口径、基准日期的可比性检查。
- 实现报价偏离与准时交付率计算，并定义最小履约样本数量。
- 明确拒绝未知模板；只覆盖空文本、缺列、错误日期、不可比报价和无历史数据等关键错误。

**交付物**

- 三个固定模板解析器、事实 Schema、确定性计算函数、样例材料和测试。

**完成判定**

- 支持范围内的事实和计算结果能定位并复算到原文件页码、单元格或 CSV 行。
- 无历史数据产生“历史数据不足”，不触发低履约率规则。
- 未知或损坏模板明确失败，不输出猜测结果。
- 系统不把文档字段检查描述为权威真实性验证。

### Day 6：知识库、混合检索、引用与评测

**目标工时：约 6 至 7 小时**

**任务**

- 准备 5 篇公开或模拟制度、SOP 和历史案例。
- 实现文档版本、生效期、章节或页码等最小引用元数据。
- 实现分块、PostgreSQL 全文索引、Embedding、pgvector 和一次性幂等入库。
- 实现全文召回、向量召回和简单 RRF 结果融合。
- 建立 5 至 8 个检索问题及期望引用，实现引用输出和稳定的“证据不足”。

**交付物**

- `data/knowledge/` 五篇资料、一次性入库命令、`evidence` 检索接口和小型评测集。

**完成判定**

- 五篇资料可重复入库且不产生重复分块。
- 每个引用能定位文档版本和页码。
- 5 至 8 个固定问题返回预期引用；无证据问题稳定返回“证据不足”。
- 本期不宣称通用检索质量，不实现权限过滤、增量索引或独立重排。

### Day 7：两个受控 Agent 与 LangGraph 恢复

**目标工时：约 6 至 7 小时**

**任务**

- 实现一个模型适配器，以及供应商分析 Agent 和证据 Agent 的两套 Pydantic 输出。
- 使用固定假适配器覆盖成功、模型失败和无证据路径。
- 只为供应商准入建立固定 LangGraph：解析、规则、分析、检索、证据审校和等待审批。
- 保存工作流与节点运行状态、输入输出引用和错误码。
- 通过一个可控失败案例验证从失败节点恢复并跳过已成功节点。

**交付物**

- 两个受控 Agent、一个准入工作流、恢复接口和集成测试。

**完成判定**

- Agent 不能直接修改状态、批准案件或绕过引用校验。
- 正常准入和补件案例经准入工作流跑通；采购例外继续使用确定性后端流程。
- 指定失败节点恢复后不重复执行已成功节点。
- 解析失败、模型超时和证据不足被记录为三种不同结果。

## 保持完整度的取舍规则

若进度落后，先保证正常准入主线，再保证最小采购例外边界：

1. 管理员入口不进入本期；时间有余时只增加只读追踪页。
2. 知识库固定 5 篇，检索问题固定 5 至 8 个。
3. 前端保持登录、队列和统一案件详情，不新增独立管理后台。
4. 只接一个 OpenAI-compatible 模型提供方，不做多厂商切换界面。
5. Docker Compose 只保证应用和 PostgreSQL，不增加反向代理或独立观测系统。

不得缩减：正常准入主线、单 PR 例外范围、五条启用规则、提交人与审批人隔离、追加式审计、三类固定模板来源定位、全文与向量融合、引用与无证据拒答、两个受控 Agent、一个可验证恢复场景和关键自动化测试。

## 进度失控时的停止线
