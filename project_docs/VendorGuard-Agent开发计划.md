### M1：先看到 Agent 工作

具体文件取舍、工具契约、实施顺序与第一条命令见 [M1 实施方案](VendorGuard-M1实施方案.md)。2026-09-10 M1 步骤 A-E 完成并通过一次外部评审闭环：`check_materials` 工具与 198 项单测/ruff/format/mypy 全绿，qwen3.7-flash 自动工具选择下正常/缺项/未知三案例入 `logs/agent-runs/`；E3 实验（纠正预算 1→2）验证机制后按规范回滚。

评审一轮修正记录：首轮真实“未知”案例经核查不忠实（模型把自己传参失败归因成用户材料问题，并声称“已触发人工审核流程”），当时“三案例均忠实”的结论过满，已撤回。修正后空回答/截断回答/迟到回答一律失败，被拒调用也入流水含原始参数；“缺失输入触发明确追问”当时以问号判据实证过一次（logs/agent-runs/20260910T111620458424.json，kind=question），该判据在二轮评审中被认定可绕过并撤销（见下）。

评审二轮修正记录：带问号的结论性文本可绕过工具背书，问号判据被撤销，追问改为显式工具 `ask_user`——纯文本一律不能作出口，追问经工具事件入档；`ask_user` 参数错误获得专属纠正桶（其余错误仍共享一次），纯文本纠正与用尽分支也带正文预览入事件。208 项单测/ruff/format/mypy 全绿。四场景复测：正常/缺件/未知通过，其中未知案例是“校验成功后经 ask_user 切题追问”的教科书链条；超范围交付率场景三次运行三种死因（空参数、`prompt` 别名、`null` 伪造），每次均为安全失败、伪造全被拦截，但未达成切题追问，记为已知限制：该模型在此场景行为高方差，随 M2 会话制（追问后接受补充并继续）消解。边界声明：`ask_user` 只能证明模型选择了追问，不能证明问题文本未夹带结论，忠实性仍靠提示词约束与案例验证，不宣称完全解决。

先确认现有模型服务支持 tool calling，使用对应官方 SDK；模型和凭证可用性在实施时核对，不在文档中假设已经配置。M1 接入业务工具 `check_materials` 与交互控制工具 `ask_user`（追问控制不计入 M1-M3 三个业务工具总数），内部复用规则纯函数，输入采用明确标注的结构化样例。

实现模型请求、工具参数校验、工具执行、结果回传和再次生成；加入 PRD 规定的轮数、工具次数与超时限制。业务规则工具只读或纯计算，不连接案件写入流程。

完成判据：一次真实模型运行有可查看的 tool call 参数、工具结果和最终回答；缺失输入能触发明确追问；使用模型响应替身验证未知工具、非法参数和循环上限。替身测试与真实模型演示分开记录。

理解检查：开发者能沿一次记录讲清“模型提出调用、程序执行工具、结果回到模型”，并修改一个工具参数或校验条件后运行验证。

### M3：把依据接进工具循环

详细文件边界、数据与工具契约、检索方案、实施步骤与验收清单见 [M3 实施方案](VendorGuard-M3实施方案.md)。

按 [PRD 的 RAG 核心范围](VendorGuard-PRD.md#rag-核心范围) 分三步，每步跑通后再继续：

1. 只处理两份现行内部制度，复用章节与表格行解析，输出可核对原文的扁平片段；不接数据库入库。
2. 完成本地 embedding 缓存与单路 Top-5 检索，先从命令行查看返回原文，再包装为 `search_policy`。
3. 接入 Agent 报告与引用检查，运行 PRD 选定的 8 题，逐题记录正确依据、边界处理和错误引用；保留一次失败分析。

完成判据：结构化报告通过 Schema、已核对事实字段、实际规则结果和本次检索节点引用校验；自由文本是否受引用支持由固定案例人工核对。补充后重新检索；用旧制度和外部法规候选元数据验证版本清单过滤；所选 8 题按各自金标准完成验收，失败时定位并修复当前实现，不先扩充检索架构。记录语料、模型、题目、真实结果及原评测中未覆盖的 7 题。关键词与向量对比是具体漏检后的可选实验。

2026-09-15 方案修订：本期片段清单与 embedding 缓存只含两份现行制度的 22 条；全量 274 条是已有解析器的基线，负例版本与外部法规保留在仓库，用候选元数据混入测试证明排序前过滤有效，无需为负例生成 embedding。最终制度引用回指 `KnowledgeNode`，不引用召回用的 `chunk_key`；报告的结构化事实字段、规则 ID 与结果对应本次成功的 `check_materials`，第二轮补充后重新检索。BM25（纯 Python 字符二元组）和全量索引只在闭环后针对具体漏检做可选实验；embedding 模型实施时先探针复核可用性、维度与归一化。

2026-09-15 补一次实测（影响 M3-3 的可复现口径）：同一批正文两次独立构建的向量**不是逐分量相同**——22528 个分量里 7168 个有差异，最大 2.0e-4。因此"同一查询的 Top-5 可复现"只能绑定到**固定的缓存文件**，不能宣称模型输出稳定；缓存除了省调用，还承担"冻结向量"的作用。近似并列的分数跨重建可能换位，评测结论要写明用的是哪份缓存。

2026-09-15 M3-3 聚焦测试与验证：`retrieval/search.py` 做单路向量检索——先按现行白名单过滤候选，再算精确 cosine，分数降序、同分按 `chunk_key`，取 Top-K（缺省与上限均为 5）；查询参数问题（空、过长、`top_k` 越界）抛 `QueryError` 留给模型纠正，配置类失败（候选被过滤光、向量与片段数量不符、查询与缓存维度不符）抛 `SearchError` 直接中断而不用空结果冒充"没有依据"。新增 18 项单测全部用替身，关键是负例向量被造成与查询同向（余弦 1.0）：断言它们不返回、而分数更低的现行片段返回，证明过滤发生在打分之前。命令行验证 `scripts/preview_search.py`（真实缓存）：查询"关键物料品类是否可以先准入后补交质量证书"返回确定的 Top-5，含 `node_key`、定位、字符区间与原文，首位是"质量证书对关键物料品类属于必需材料，不再允许通过后再补交"；重复检索排序一致。全量单测 296 通过，Ruff、格式检查与 mypy 全绿。实现待粘贴后判绿。

M3-3 另一条实测限制：查询向量按设计每次现算，两次检索的**分数在第 4 位小数上会漂移**（实测 0.8236 / 0.8237）而排序不变。排序稳定依赖分差远大于该漂移，这再次说明分数不能当阈值；评测若出现 1e-3 量级的并列，要记成并列而不是断言单一名次。

2026-09-15 M3-4 测试与验证：`agent.py` 的循环接入 `search_policy`——工具声明 `query`（必填）与 `top_k`；新增启动装载 `load_policy_index()`，读片段清单并取回或构建向量缓存，清单缺失、缓存损坏或 embedding 不可用一律归一为启动错误（退出码 2）；成功的检索把本次真实返回的 `node_key` 与原文写进 `returned_nodes`（M3-5 的引用闸门只认这份集合），交给模型的工具结果含 `as_of`、`scope` 与每条节点的 `node_key`/定位/原文而**不含分数**；查询参数问题（含 `top_k` 越界）走共享纠正通道，检索配置或 embedding 不可用则直接失败且不再请求结论；工具预算与"一次响应只允许一个工具调用"沿用 M2。新增 9 项替身用例（含逐字段核对交给模型的 JSON、无索引时直接失败、embedding 失败时不继续请求）。全量单测 305 通过，Ruff、格式检查与 mypy 全绿；开发者粘贴后已在仓库跑绿，并用"把模型端点指向死端口"的方式实测 CLI 启动路径：打印 `[制度检索] 已装载 22 条现行制度片段` 后才进入循环，退出码 1（模型请求失败），未消耗真实模型调用。

M3-4 的一条设计取舍：检索**不要求先读过材料或先校验**。方案只钉住"未读材料不能 check"（M2 已有），检索是只读查询，提前查制度不构成越权；顺序仍由提示词引导（先校验事实、再取制度依据）。

## 控制范围

任何新增组件先对应一个当前案例中的具体问题。默认范围只有一个 Agent、三个业务工具、一种材料和一个工作台；需要增加时先说明哪个现有案例无法完成。

每次功能改动运行相关测试和必要的 lint、类型检查。只有修改数据库时才做迁移验证；纯文档改动检查链接与一致性即可。真实模型结果具有波动，记录实测情况，不把一次成功当作质量保证。
