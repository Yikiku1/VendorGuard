## 1. 完整链路的分层与不可退让的约束

一次审查从"用户丢来一份 PDF"到"带来源的初审建议"，经过四层。每层都有明确的
不可信假设与对应的程序侧义务：

```text
材料层    read_material      模型只能读程序白名单内的材料; 扫描件明确拒绝, 不静默降级
事实层    check_materials    模型读数不可信 -> 每个值必须在所声明的来源里字面命中
规则层    evaluate_rule      纯函数, 与模型无关; 日期状态由程序按参考日期派生
依据层    search_policy      只返回参考日期下生效的版本; 引用标签必须来自真实返回
出口层    submit_report      纯文本不是结论出口; 越权宣告准入被机械拦截
```

三条边界是结构性的，不靠提示词自觉——这是整个项目最重要的设计主张：

| 边界 | 机制 | 为什么不能只靠提示词 |
| --- | --- | --- |
| 模型不能编造事实 | 值必须在其声明的来源文本里字面命中，日期比较数字组 | 提示词约束不住模型"顺手补一个合理日期" |
| 模型不能伪造出处 | 引用标签必须属于本次检索真实返回的集合 | 编造一个像真的定位符对模型毫无成本 |
| 模型不能宣告准入结论 | 命中"准入通过""建议批准"等措辞即拒绝并要求改写 | 与 M1 的结论出口问题同源，实测已复现 |

**本期明确不做**：访问数据库、写案件状态、跑迁移、前端。产出只是**初审建议**，
不是供应商准入批准。

## 2. 已实现的纵切与实测记录（2026-09-11）

### 2.1 新增文件

| 文件 | 职责 |
| --- | --- |
| `src/vendorguard/materials.py` | PDF 逐页提取、扫描件判定、来源字面核对（`SourceTexts`） |
| `src/vendorguard/material_facts.py` | 提取层事实、日期状态派生、字面核对、规则输入组装 |
| `src/vendorguard/retrieval.py` | BM25 本地检索 + 版本生效期过滤 |
| `src/vendorguard/agent_session.py` | 跨轮状态、轮次上限、用户补充归属 |
| `src/vendorguard/review.py` | 工具循环（`_ReviewLoop`，每个工具一个处理函数）、报告渲染、CLI |
| `scripts/make_demo_materials.py` | 生成四份可复现样例 PDF（含扫描件） |

`review.py` 的结构：工具参数解析与文字检查（`verify_citation_labels` /
`find_approval_claims`）是纯函数；单轮循环与各工具处理集中在 `_ReviewLoop`，
按工具拆成 `_handle_*` 方法；`run_review()` 只是薄封装。工具错误统一走
`_deny()`——正常返回表示错误已回传、循环继续让模型纠正，纠正用尽则抛出
`_ToolDenied` 终止本轮。这样把原先散落的 11 处"检查返回值再 return 失败"
收敛成一条路径，最长函数从约 500 行降到 74 行。

依赖新增仅两项：`pypdf` 进运行时，`reportlab` 进 dev 组（仅用于生成样例）。
不引入 `pdfplumber`（更重）与 `pymupdf`（AGPL）。

### 2.3 运行期暴露并修掉的问题

这几条是真实运行才发现的，值得记录——它们说明"能跑"与"可信"是两件事：

1. **模型在报告叙述里宣告准入结论。** 首次运行输出"建议批准该供应商准入"。
   提示词已禁止，模型仍写。加 `find_approval_claims()` 机械拦截后，模型改写成
   "材料形式审查通过"。拦截需处理否定：`不构成准入批准` 是免责声明，不能误伤。
2. **追问时用户看不到已查出的问题。** 过期材料场景模型选择追问清单完整性，
   而已确认的"执照已过期"没有出现在用户可见文本里。改为 `_render_question()`
   由程序渲染已发现的处置事项，不依赖模型转述。
3. **勾选框不构成可读事实。** 只放 `☑` 时模型无法判断清单是否齐全；样例加
   `清单状态: 已齐全` 明确语句后才稳定。这与"布尔判断只能核对来源存在、
   不能验证判断本身"的限制一致。
4. **工具的来源要求必须写在 Schema 描述里。** 模型曾提交事实却不给 `sources`。
   该错误消耗共享纠正桶，第二次仍犯即失败——这是预期行为，但把要求写进工具
   描述后不再发生。

### 2.4 检索评测结果（15 题，`data/evals/rag_phase1.json`）

| 指标 | 结果 |
| --- | --- |
| 可回答题的必需目标全部命中 | **9/10** |
| 因日期失效而应排除的版本正确排除 | **6/6** |
| 答案充分性约束（`no_answer` / 对抗题） | **未实现**，7 处有效版本仍被召回 |

**必须如实记录的两条限制：**

- **未命中的 1 题**是 `ccc_product_certification`：query 用"CCC"，而目标条文
  写"列入目录的产品"，字面不重叠。这是 CJK 二元组稀疏检索的词汇鸿沟，
  需要同义词扩展或向量召回才能闭合。
- **`no_answer` 类约束未实现**。评测集里 `no_answer` 与对抗题的
  `forbidden_edition_keys` 表达的是"**该版本不该作为这个问题的依据**"，
  而不是"该版本已失效"——例如"仅凭执照图片能否确认真实性"本身就无可依据。
  我的检索层只实现了日期有效性过滤，**没有任何"证据是否足以回答"的判断**，
  因此这些有效版本仍会被召回。这不是检索 bug，是**答案充分性机制缺失**，
  属于 M4 范围。报告里已有"本次未检索到可引用片段时列为待人工确认"的兜底，
  但不能替代充分性判断。

## 3. M4：把机制补到能自证

M4 不再加新能力，只做三件事：**补充分性判断、补可复现性、补边界说明**。

### 3.1 答案充分性（最高优先级）

**问题**：检索返回了相关片段，不等于片段能回答这个问题。当前报告只会说
"未检索到片段时需人工确认"，但片段存在而不足时没有任何检查。

**方案**：引入 `assess_sufficiency(hit, question) -> Sufficient | Insufficient(reason)`，
在 `search_policy` 之后、`submit_report` 之前执行。判定输入为检索命中的
版本、定位符与原文，输出三态：

| 状态 | 判据（可机械验证的部分） | 报告影响 |
| --- | --- | --- |
| `sufficient` | 命中片段含问题的关键实体与结论词 | 正常成稿 |
| `insufficient_no_evidence` | 无命中，或命中版本全部被日期过滤 | 列为待人工确认，禁止下结论 |
| `insufficient_unanswerable` | 问题属于"需要语料外事实"（真实性、目录归属等） | 明确说明无法依据现有语料判断 |

第三类是难点：它需要识别"这个问题本质不可回答"。做法不是让模型自由心证，
而是**要求模型显式声明它引用了哪个片段支撑哪句话**，程序核对
（`citation -> claim` 绑定）。模型无法为一句没有依据的话绑定真实片段，
该声明就会失败，从而被迫走 `insufficient` 分支。这与前三层的思路一致：
不问模型"你是否确信"，只问"你的结论对应哪些可核对的引用"。

**验收**：评测集 5 道 `no_answer` / 对抗题不再返回可被引用的有效版本作为依据，
或明确标注为 `insufficient_unanswerable`；15 题全部有明确三态归属。

### 3.2 评测自动化

把第 2.4 节的手工统计变成可重复运行的评测命令：

```bash
python -m vendorguard.eval data/evals/rag_phase1.json
```

输出每题的三态、命中情况、被过滤版本，以及汇总指标，退出码反映是否达标。
**门槛**：可回答题目标命中率不低于 9/10，日期过滤 6/6，充分性判定无漏报。

### 3.3 词汇鸿沟

CCC 那题要么加受控同义词表（`CCC -> 强制性产品认证 / 列入目录的产品`），
要么引入向量召回做混合检索。**取舍**：先做前者——一份显式同义词表可以
单测、可以复核，而向量召回会引入 embedding 依赖且降低可解释性。仅当同义词表
无法覆盖时再评估混合检索。项目已有 `pgvector` 依赖与 RAG 持久化模型，
但本期仍是本地扁平检索，不入库。

### 3.4 未做的可复现性

- `--supplement` 目前是脚本化参数，交互式补录也可以走通，但没有把"一次完整
  多轮会话"固化为回归测试用的脚本化场景。
- 扫描件之外的失败模式（加密 PDF、损坏文件、多页混合）已有代码分支但缺少
  真实样本验证。
- 报告未做 HTML/PDF 导出，只有 Markdown 文本。

## 4. M5 及以后（只在被问到方向时展开，不作为承诺）

按价值排序，每项都注明它验证什么能力：

1. **落库与案件闭环**：把初审报告挂到案件上，写案件状态。**验证**：报告从
   一次性文本变成可追溯业务对象；需要处理幂等与事务边界。
2. **前端演示**：上传材料、看追问、看报告的最小页面。**验证**：产品可用性，
   与 Agent 能力无关，但面试演示时最直观。
3. **规则扩展**：启用 `VEN-003`（质量证书剩余 90 天）等已设计未启用的规则。
   **验证**：规则引擎的可扩展性；`certificate_remaining_days()` 已有现成调用方。
4. **多材料与多品类**：当前一次审查一份执照，品类清单已从材料读出但未参与
   规则分支。**验证**：跨材料事实聚合与冲突处理。
5. **混合检索**：向量 + BM25 融合，需先有 3.3 的结论。

## 5. 已知缺口清单（不得在对外材料里含糊）

| 缺口 | 性质 | 影响 |
| --- | --- | --- |
| 答案充分性未实现 | 机制缺失 | `no_answer` 类问题仍会返回可引用片段（7 处） |
| CCC 题未命中 | 检索局限 | 10 题中 1 题必需目标召回不到 |
| `category_required_documents_complete` 只验来源 | 固有不对称 | 布尔判断本身正确与否只能人工确认 |
| 不访问数据库、不写案件状态 | 范围边界 | 报告不改变任何业务状态 |
| 无前端 | 范围边界 | 只能命令行演示 |
| 覆盖率未测量 | 质量门缺口 | 无法量化未覆盖分支 |
| 未验证多种失败材料 | 验证缺口 | 加密/损坏样本无真实运行证据 |
| 单一模型单一版本 | 泛化性 | 仅 `qwen3.7-flash` 实测，未跨模型对比 |

## 6. 实施顺序建议

若继续推进，按此顺序——每步都能独立验证，且不依赖后续步骤：

| 步骤 | 内容 | 完成判据 |
| --- | --- | --- |
| A | 答案充分性 + `citation -> claim` 绑定 | 15 题全部有明确三态；5 道 no_answer 不再误给依据 |
| B | 评测命令化 `vendorguard.eval` | 一条命令复现全部指标，退出码可用 |
| C | 同义词表闭合 CCC 题 | 可回答题目标命中率 10/10 |
| D | 失败材料样本补齐 | 加密/损坏/混合三类有真实运行记录 |
| E | 报告导出（Markdown → HTML） | 可选，服务演示 |
| F | 入库与案件闭环 | 需要先定事务与幂等边界 |

前四步都在当前"不访问数据库"的边界内，可以独立完成。
