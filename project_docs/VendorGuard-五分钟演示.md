# VendorGuard 五分钟演示脚本

> 用途：现场演示（或录屏）时照着走，每一步都给出**预期结果**。所有指标只引用
> 2026-09-16 的真实验收结果（模型 `qwen3.8-max`），模型波动按实际写。
> 相关文档：[README](../README.md)、[当前项目事实](../PROJECT_CONTEXT.md)。

## 0. 开演前 30 秒（只在第一次做）

```powershell
docker compose up -d database
uv run --no-sync uvicorn vendorguard.app:create_app --factory
```

预期：控制台没有报错，浏览器打开 <http://127.0.0.1:8000/workbench> 能看到登录区域
（**未登录时页面只有登录框**，主区域不出现）。
若启动失败，按提示补齐 `.env` 或先跑 `scripts/build_embedding_cache.py`——
这是有意设计：检索数据不可用时**启动就失败**，不会装作"制度里没有依据"。

## 1. 登录（20 秒）

用 `.env` 里的 `demo.specialist` 登录（开发时也可以用管理员账号 `admin`，口令由
`VENDORGUARD_DEMO_ADMIN_PASSWORD` 决定、不配置时沿用 `demo.specialist` 的口令；
两个账号看到的"最近审查"互相隔离，各看各的记录——顺带也就是"跨用户读不到"的现场演示）。

预期：顶栏出现用户名与角色；左侧"最近审查"列出本轮验收留下的记录，含状态徽标
（`报告完成` / `失败`）与"重跑自 xxxxxxxx"这类关联。

讲解词：Token 只放在这个标签页的 `sessionStorage`；过期或无效时页面自动清掉 Token 回到登录。

## 2. 正常路径：完整材料（90 秒）

"新建审查"里选 `data/demo/materials/license_complete.pdf`，审查要求填
"请检查这家供应商的材料是否满足准入要求."，参考日期 `2026-09-01`，点"开始审查"。

预期（本轮实测）：

- 按钮立刻变成"审查中…"并禁用，状态行写"审查中: 这一轮要读取材料, 校验事实并检索制度。"；
- 完成后状态为`报告完成 · 更新于 …`，运行轮次显示
  `第 1 轮 · 报告 · qwen3.8-max · 模型请求 4 次 / 工具调用 4 次`；
- 结构化报告 2 条发现：一条讲营业执照有效期（2027-08-31 在评估日期之后，材料层面未过期），
  一条讲清单齐全；
- **材料来源**：`material@page:1` + "查看材料 第 1 页"按钮 → 点开是原始 PDF，浏览器直接停在那一页；
- **制度引用**：4 条，点开任意一条能看到标题、定位路径、制度版本与**本次运行保存的原文**；
- **工具轨迹**：`read_material → check_materials → search_policy → submit_report`，默认折叠；
- 底部固定提示"初审报告不是准入决定…"。

## 3. 补充路径：缺有效期 → 追问 → 第二轮（90 秒）

选 `data/demo/materials/license_missing_date.pdf`，同样的请求与日期，点"开始审查"。

预期（本轮实测）：

- 第一轮是**追问**（`第 1 轮 · 追问 · 模型请求 3 次 / 工具调用 3 次`），模型问"请提供营业执照有效期截止日"；
- 此时动作区**只出现补充表单**（`可执行动作: 补充材料`）；
- 填入"补充说明: 营业执照有效期至 2030年01月31日"并提交；
- 完成后是**两轮**记录（第一轮追问不丢），报告结论基于补充日期；
- **材料来源**变成两条：`用户补充 第 1 轮`（直接显示原文）与 `material@page:2`（定位到第 2 页）；
- 轨迹里能看到第二轮**重新**执行了 `read_material → check_materials → search_policy → submit_report`。

讲解词：第二轮是独立的一次运行——它不沿用第一轮的检索结果，报告里的制度引用只能来自第二轮
自己检索到的节点；补充只允许一次，想改变意见要创建重查记录。

## 4. 无依据路径（40 秒）

材料仍用完整样例，请求改成"请说明这份材料是否需要提供环保检测报告, 并引用现行制度的具体条款."

预期（本轮实测）：报告区顶部出现
`依据不足: 已检索现行准入制度与分品类必需材料清单，未发现任何条款将环保检测报告列为必需材料…`。

讲解词：检索不设分数阈值、恒返回 Top-5，**"排在前面的条款"不等于"能支持结论"**；
模型找不到依据时必须写清缺哪类依据，而不是硬答。

## 5. 失败与重跑（60 秒）

失败路径用扫描件最快：选 `data/demo/materials/license_scanned.pdf`。

预期：状态`失败`，事实里写 `[material_scanned_unsupported] 扫描件暂不支持…（这类失败不能用原记录重跑）`，
运行轮次为空、轨迹为空——**材料层就拒绝了，没有发模型请求**，也没有 OCR。

再看一次真实运行失败与重跑（本轮实测的记录）：

1. 打开那条 `[agent_run_failed] 模型请求失败: Connection error.` 的记录
   （模型端点不可达造成；1 次模型请求、0 次工具调用）；
2. 点"用原记录重跑"；
3. 预期：**创建了一条新记录**（列表里显示"重跑自 …"），旧失败记录一字未改；
   新记录跑出正常报告（`第 1 轮 · 报告 · 模型请求 4 次 / 工具调用 4 次`）。

讲解词：重跑不是改这条记录，而是复制材料与原请求、建一条新记录并用 `retry_of_review_id` 关联；
接口不接受自选模型、路径或状态参数——重跑资格由服务端算出的 `allowed_actions` 决定，与页面按钮同源。

## 6. 收尾：三条边界（30 秒）

1. **初审报告不是准入决定**：报告确认只表示用户看过并接受；确认与重查都不会调用准入审批，
   也不改案件或供应商状态（反馈响应里明确写 `business_state_changed=false`）。
2. **来源可核对**：材料来源定位到 PDF 页码（或显示用户补充原文），制度引用展开的是**本次保存的原文**，
   查看时不会重新检索。
3. **失败留痕**：失败的轮次、错误码与工具事件都留在记录里，可对比前后运行。

## 7. 常见追问（可以顺手指）

- **为什么不用前端框架？** 首版要求是"能演示、能核对来源"：原生 HTML/CSS/JS + FastAPI 静态资源就够了，
  少一层构建链就少一处出错点；按钮状态全部由服务端的 `allowed_actions` 驱动。
- **为什么记录不写数据库？** 审查记录是演示证据，不是业务案件：放本地忽略目录
  （`var/reviews/`）既不动业务表，也能让"失败记录"随手可查、可删。
- **为什么不做实时轨迹？** 一轮审查是同步阻塞的，首版用线程池等它跑完再一次性展示；
  WebSocket/SSE、后台队列、节点级恢复都不在本阶段范围内。
