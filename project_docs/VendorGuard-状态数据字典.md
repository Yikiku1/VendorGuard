# VendorGuard 状态数据字典

> 2026-09-08 范围调整：本文保留已有案件与数据库的兼容定义，修改这些模块时查阅。它不要求新 Agent 实现全部状态；当前产品范围见 [PRD](VendorGuard-PRD.md)。报告确认不等于准入批准，技术失败也不等于业务拒绝。

> 文档类型：一期领域状态基线  
> 适用范围：供应商准入与采购申请例外审批  
> 目标：统一产品文案、后端枚举、数据库约束、状态迁移和测试用例

## 1. 为什么要拆成五类状态

同一时刻，一个供应商相关流程可能同时出现以下事实：

- 供应商资格为 `candidate`，表示尚未进入 AVL；
- 准入案件为 `analyzing`，表示本次申请正在分析；
- 工作流运行为 `failed`，表示本次技术执行失败；
- 某项风险的证据充分性为 `insufficient`，表示检索成功但依据不足。

这些状态描述的对象不同，不能共用一个 `status` 枚举，也不能互相替代。特别是：

- 工作流失败不等于准入被拒绝；
- 证据不足不等于模型或检索服务故障；
- 采购例外获批不等于供应商资格获批；
- 案件归档不删除最终决定、规则命中和审计历史。

## 2. 通用约定

| 项目 | 约定 |
| --- | --- |
| 存储值 | 使用小写 `snake_case` 英文代码，例如 `pending_approval` |
| 页面文案 | 使用本字典中的中文名称，不直接向用户展示英文代码 |
| 状态修改 | 只能通过明确的领域动作迁移，不能由前端直接指定任意目标状态 |
| 非法迁移 | 拒绝请求，不修改原状态，并记录必要的安全或业务日志 |
| 审计 | 每次成功迁移记录对象、原状态、新状态、操作者、原因和时间 |
| 并发 | 更新时校验原状态，避免两个审批动作互相覆盖 |
| 历史 | 工作流失败、规则命中、人工决定和豁免记录均不得被后续状态覆盖 |

`archived` 表示案件不再参与日常待办，不代表删除。案件的最终批准或拒绝结果必须继续保存在决定记录中。

## 3. 供应商资格状态

**所属对象**：供应商 `Supplier`  
**回答的问题**：该供应商当前是否具备常规采购资格？  
**初始状态**：`candidate`

| 状态代码 | 中文名称 | 定义 | 允许迁移到 |
| --- | --- | --- | --- |
| `candidate` | 候选 | 已登记供应商，但尚未取得当前有效的准入资格 | `approved`、`rejected` |
| `approved` | 已准入 | 已通过准入审批且资格仍在有效期内，可进入 AVL | `suspended`、`expired` |
| `suspended` | 已暂停 | 原有资格被临时冻结，暂停期间不能进入 AVL | `approved`、`expired`、`rejected` |
| `expired` | 已过期 | 准入资格超过有效期，不能进入 AVL | `candidate` |
| `rejected` | 未通过 | 最近一次资格审查未通过，不能进入 AVL | `candidate` |

### 3.1 迁移条件

| 迁移 | 触发动作 | 必要条件 |
| --- | --- | --- |
| `candidate -> approved` | 准入批准 | 关联准入案件已批准；必需审批均完成；资格有效期已确定 |
| `candidate -> rejected` | 准入拒绝 | 关联准入案件已拒绝，且拒绝理由已记录 |
| `approved -> suspended` | 暂停资格 | 有权限人员给出暂停原因和生效时间 |
| `approved -> expired` | 资格到期 | 当前时间超过资格有效期 |
| `suspended -> approved` | 恢复资格 | 暂停事项已处理，且原资格仍在有效期内 |
| `suspended -> expired` | 暂停期间到期 | 当前时间超过资格有效期 |
| `suspended -> rejected` | 复核不通过 | 复核形成明确拒绝决定和理由 |
| `expired -> candidate` | 发起重新准入 | 必须新建准入案件，旧案件保持不变 |
| `rejected -> candidate` | 再次申请 | 必须新建准入案件，旧的拒绝决定保持不变 |

### 3.2 AVL 判定

供应商只有同时满足以下条件时才属于 AVL：

1. 资格状态为 `approved`；
2. 资格有效期尚未结束；
3. 不存在已经生效但尚未解除的暂停决定。

AVL 是查询投影，不是可手工维护的独立状态或名单。

## 4. 准入案件状态

**所属对象**：准入案件 `AdmissionCase`  
**回答的问题**：一次供应商准入申请目前走到哪一步？  
**初始状态**：`draft`

| 状态代码 | 中文名称 | 定义 | 允许迁移到 |
| --- | --- | --- | --- |
| `draft` | 草稿 | 申请已创建，仍可编辑基础信息和材料 | `pending_documents`、`analyzing` |
| `pending_documents` | 待补件 | 缺少必填材料或人工要求补充材料 | `analyzing` |
| `analyzing` | 分析中 | 正在或等待执行材料解析、事实提取和确定性规则检查 | `pending_documents`、`evidence_reviewing` |
| `evidence_reviewing` | 证据审校中 | 正在检索并核验制度、案例和风险引用 | `pending_documents`、`pending_approval` |
| `pending_approval` | 待审批 | 风险和证据已形成，等待有权限的人工决定 | `pending_documents`、`approved`、`rejected` |
| `approved` | 已批准 | 本次准入申请已通过，最终决定已形成 | `archived` |
| `rejected` | 已拒绝 | 本次准入申请未通过，最终决定和理由已形成 | `archived` |
| `archived` | 已归档 | 案件退出日常待办，历史结果仍可查询 | 无 |

### 4.1 关键迁移规则

- `draft -> analyzing` 前必须完成提交动作；材料明显不完整时进入 `pending_documents`。
- 分析过程中发现业务材料缺失时进入 `pending_documents`。
- 解析器、检索或模型调用异常时，案件保持当前业务状态；对应工作流运行进入 `failed`。
- `pending_approval -> pending_documents` 表示审批人要求补件。原规则命中、证据和审批意见不能删除。
- `approved` 必须同步产生供应商资格变化；`rejected` 不允许供应商进入 AVL。
- 已批准或已拒绝的案件不能重新打开。再次申请必须创建新案件。
- `archived` 后仍需通过决定记录判断该案件最终是批准还是拒绝。

## 5. 采购例外案件状态

**所属对象**：采购例外案件 `ProcurementExceptionCase`  
**回答的问题**：某一个 PR 使用非 AVL 供应商的例外申请是否可用？  
**初始状态**：`draft`

| 状态代码 | 中文名称 | 定义 | 允许迁移到 |
| --- | --- | --- | --- |
| `draft` | 草稿 | 例外申请已创建，原因、范围、有效期和附件仍可编辑 | `pending_approval` |
| `pending_approval` | 待审批 | 等待审批矩阵要求的人员分别作出决定 | `approved`、`rejected` |
| `approved` | 已批准 | 只允许关联 PR 在批准范围和有效期内继续 | `expired`、`archived` |
| `rejected` | 已拒绝 | 关联 PR 不得基于本例外继续 | `archived` |
| `expired` | 已过期 | 已批准例外超过有效期，不能继续使用 | `archived` |
| `archived` | 已归档 | 案件退出日常待办，历史决定仍可查询 | 无 |

### 5.1 关键迁移规则

- 一个例外案件只能绑定一个 PR，不允许更换 PR，也不能跨 PR 复用。
- `pending_approval -> approved` 前必须满足审批矩阵；关键物料需要采购经理和质量经理分别批准。
- 申请人不能审批自己提交的例外。
- 任一必需审批角色拒绝后，案件进入 `rejected`，不能继续等待其他批准来覆盖拒绝。
- `approved` 只改变关联 PR 的放行结果，不改变供应商资格，不把供应商加入 AVL。
- 当前时间超过 `valid_until` 时，例外由 `approved` 进入 `expired`。
- 已过期或已拒绝的例外不能恢复；仍需采购时应重新创建例外案件。
- 尚未到期但业务已完成的例外可以归档；归档不会扩大或延长批准范围。

## 6. 工作流运行状态

**所属对象**：工作流运行 `WorkflowRun`  
**回答的问题**：一次解析、规则、检索或 Agent 编排在技术上执行得怎样？  
**初始状态**：`queued`

| 状态代码 | 中文名称 | 定义 | 允许迁移到 |
| --- | --- | --- | --- |
| `queued` | 已排队 | 运行记录已创建，尚未开始执行 | `running`、`failed` |
| `running` | 运行中 | 至少一个节点正在执行，运行尚未结束 | `succeeded`、`failed` |
| `succeeded` | 运行成功 | 本次运行按预期完成并保存输出引用 | 无 |
| `failed` | 运行失败 | 本次运行因明确的技术错误未完成 | 无 |

### 6.1 关键迁移规则

- `failed` 只表示技术执行失败，不自动改变准入案件或采购例外案件的业务结论。
- 失败记录必须保存失败节点、稳定错误码、可安全展示的摘要和发生时间。
- 重试时新建一条 `queued` 运行记录，并通过 `retry_of_run_id` 指向失败运行。
- 重试不得把旧的 `failed` 记录改回 `running`，也不得重复创建已经成功保存的规则命中、审批任务或审计事件。
- `succeeded` 表示技术运行完成，不表示证据一定充分，也不表示案件已获批准。

## 7. 证据充分性状态

**所属对象**：风险项的证据审校结果  
**回答的问题**：已完成的检索和引用核验，是否足以支持这项风险解释？  
**初始值**：空值，表示尚未完成评估

| 状态代码 | 中文名称 | 定义 | 后续变化 |
| --- | --- | --- | --- |
| `sufficient` | 证据充分 | 至少存在满足来源、有效期、权限和引用定位要求的依据 | 引用失效时可重新评估为 `insufficient` |
| `insufficient` | 证据不足 | 检索已正常完成，但没有找到满足要求的依据 | 补充知识或重新检索后可评估为 `sufficient` |

### 7.1 关键判断规则

- 尚未运行证据检索时使用空值，不增加 `not_evaluated` 作为第三种充分性结论。
- 检索超时、模型异常、引用校验程序报错属于工作流 `failed`，不能写成 `insufficient`。
- `insufficient` 不自动导致案件拒绝，应将缺失情况和已检索范围展示给人工审批人。
- 每次重新评估均保留使用的知识版本、引用结果和运行记录；不能只覆盖旧结论而丢失依据。
- 若页面展示案件级证据状态，则它是风险项状态的汇总：任一必须解释的风险为 `insufficient`，案件级显示“证据不足”。

## 8. 五类状态之间的关系

| 发生的事情 | 应改变的状态 | 不应被自动改变的状态 |
| --- | --- | --- |
| 材料解析器超时 | 工作流运行变为 `failed` | 准入案件不能变为 `rejected`；证据不能变为 `insufficient` |
| 正常检索但没有可靠引用 | 证据充分性变为 `insufficient` | 工作流不能变为 `failed`；案件不能自动拒绝 |
| 准入审批通过 | 准入案件变为 `approved`，供应商资格变为 `approved` | 采购例外案件不受影响 |
| PR 例外审批通过 | 采购例外案件变为 `approved` | 供应商资格不变，其他 PR 不受影响 |
| 供应商资格到期 | 供应商资格变为 `expired`，退出 AVL | 历史准入案件和决定不变 |
| 审批人要求补材料 | 准入案件变为 `pending_documents` | 已有规则命中、证据和审批意见不删除 |

## 9. 后续实现时的最小验证清单

后续编写状态迁移代码时，至少把以下场景转成自动化测试：

1. 合法迁移成功，并追加一条状态变化审计事件。
2. 非法迁移被拒绝，原状态和审计历史不被篡改。
3. 两个并发审批不能互相覆盖或重复完成案件。
4. 工作流失败后重试会创建新运行，旧失败记录仍可查询。
5. 证据不足与技术失败产生不同的数据和页面提示。
6. 准入批准使供应商进入 AVL；采购例外批准不会使其进入 AVL。
7. 例外批准不能被另一个 PR 使用，过期后也不能继续使用。
8. 补件后重新分析不会删除第一次规则命中和审批意见。
